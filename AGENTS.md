# Работа над Atrion 2.0

Эти инструкции действуют для всего репозитория. Источник проекта — `https://github.com/alitojcubekov206-svg/atrion-2.0.git`. Назначение и текущее поведение описаны в [SPEC.md](SPEC.md), устройство — в [ARCHITECTURE.md](ARCHITECTURE.md), запуск — в [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md).

## Продуктовый курс и текущий этап

Основной будущий фокус — 2D-риггинг персонажей: скелет и анимация плоского персонажа. 3D-риггинг и создание/дизайн дома также входят в продуктовый объём. В актуальном коде пока реализованы AI Software Architect и общий 3D Design Engine; новых редакторов риггинга нет.

Текущий этап по прямому запросу пользователя — серверная реализация риггинга и дома с передачей в GitHub. Пользователь разрешил следующий этап: добавить 2D- и 3D-риггинг в интерфейс. Сохраняй существующий Design Engine; чистые контракты/evaluator размещай в shared. Backend-контракты — в [docs/DESIGN_BACKEND.md](docs/DESIGN_BACKEND.md); серверный API не означает готовность редактора.

Проектные навыки лежат в `.agents/skills`: `atrion-2d-rigging`, `atrion-3d-rigging`, `atrion-house-design`. Читай соответствующий `SKILL.md` для профильной задачи. Они не определяют произвольные права на публикацию или внешние действия.

## Перед изменениями

- Прочитай связанные документы и код; проверь `git status --short --branch`. Сохраняй пользовательские изменения. Не выполняй автоматически pull, reset, очистку файлов или обновление базы.
- Описывай отдельно существующее поведение, требования пользователя и предложения. Наличие зависимости или рекламного текста не доказывает наличие функции.
- Документы пиши на русском. Имена типов, API и путей сохраняй как в коде.
- Не добавляй внешних провайдеров по предполагаемому API; сначала проверь их официальную документацию. Не помещай ключи и пользовательские данные в документы, коммиты или сообщения.
- MCP помогает агенту работать над проектом, но не является runtime API приложения. Статус подключений и подготовленная конфигурация — в [docs/TOOLING.md](docs/TOOLING.md). Для OpenAI/Codex используй настроенный OpenAI Docs MCP, если его инструменты доступны; иначе официальную документацию через web. Не считай одну запись config доказательством действующего подключения в текущем чате.

## Границы модулей

- `src/frontend/` — браузерные компоненты, геометрическое редактирование, голос, экспорт. Не импортирует `src/backend/`.
- `src/backend/` — база, сессии, AI, квоты, серверная генерация. Не импортирует `src/frontend/`.
- `src/shared/` — чистые функции и контракты без секретов, Prisma и браузерного окружения. Изменяя контракт, проверь сервер, UI, просмотр и экспорт.
- `src/app/api/` — HTTP-маршруты. Серверные страницы `src/app/` могут обращаться к backend и рендерить frontend-компоненты; это не нарушение границы клиентского кода.
- Сохраняй `.github/CODEOWNERS`; `@frontend-developer` пока является заполнителем. Инструкция [для фронтенда и бэкенда](<инструкция фронтенд и бекенд>) сохранена, но её утверждения о Finik и деплое следует сверять с текущим кодом.

## Правила реализации

- Для приватных project/3D-маршрутов используй `requireApiUser`; проверяй владельца проекта. Auth-маршруты имеют отдельную проверку сессии и ограничение запросов.
- AI-маршруты резервируют суточную квоту и возвращают её при необработанной ошибке. Локальный fallback, успешно вернувший ответ, считается выполненным запросом.
- Сохраняй ограничение Free на 3D-генерации и возврат резервирования при ошибке. Тарифные константы — в `src/backend/plans.ts`.
- Геометрия: `size` — полные размеры до вращения; `rotation` — радианы XYZ; учитывай `repeat`, `mirror`, `mesh` в просмотре, bounds и экспорте.
- Декоративные эффекты учитывают `useEffects()` и reduced motion. Не выключай рабочий 3D-редактор вместе с декоративными сценами.
- Не выдавай AI-оценки за инженерные расчёты, печать страницы за серверный PDF, экспорт позы за анимационный skinning.
- Новое поведение сопровождай согласованными изменениями спецификации и архитектуры.

## Проверка и сдача

Для кода: `npx tsc --noEmit` и `npm run build`, как в CI. Для генератора, CSG и голосового парсера — соответствующие существующие скрипты из [DEVELOPMENT.md](docs/DEVELOPMENT.md). Добавляй проверки реальных инвариантов, а не копии реализации. Для изменений только документации достаточно проверки путей, ссылок, команд и `git diff --check`.

Не запускай `prisma db push` против неизвестной или рабочей базы как проверку. Передавай точный результат проверок и ограничения; не называй непроверенный сценарий работающим. Commit, push, публикация и сообщения другим людям выполняются в пределах прямого запроса пользователя.
