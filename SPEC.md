# Спецификация Atrion 2.0

Обязательные требования пользователя к универсальности и качеству результата: [GENERATION_QUALITY.md](docs/GENERATION_QUALITY.md). Они задают целевой стандарт для текст → 3D, 2D-риггинга и дизайна дома; текущая реализация ниже не означает автоматического достижения этого стандарта.

Статус: описание подтверждённого поведения текущего приложения и целевого продукта. База — `main` / `26ea85d`, повторно проверенная 5 октября 2026 года. Ветка `codex/backend-rigging` добавляет серверный модуль и ручные редакторы 2D/3D. Пользователь затем подтвердил генерацию персонажа и рига по тексту как главный сценарий; требования — [CHARACTER_GENERATION.md](docs/CHARACTER_GENERATION.md). Это спецификация Atrion; генерируемые приложением blueprint чужих проектов не определяют его собственные требования.

## Назначение и пользователи

Сейчас Atrion превращает текстовую идею программного продукта в технический план и предоставляет редактор концептуальных 3D-моделей. Это подтверждено README, UI, API и типами.

Последнее указание пользователя: **риггинг отложен**, текущий приоритет — **backend текст → 3D с проверкой экспорта для Unity** и **создание/дизайн дома**. Ранее подтверждённые требования риггинга сохраняются как отложенный объём. Дизайн дома включает планировку и оформление. Существующий AI Architect сохраняется.

Роли: посетитель, пользователь Free, пользователь с действующим Pro. Отдельных ролей администратора, организации и совместной команды в схеме нет.

## Тарифные правила

Источник — [plans.ts](src/backend/plans.ts). Free: максимум 5 одновременно существующих проектов, 5 успешных 3D-генераций за всё время, 25 AI-запросов в UTC-день. Pro: число проектов и 3D-генераций не ограничено этими счётчиками, AI ограничен 300 запросами в день. Удаление проекта освобождает место; удаление/сброс сцены не возвращает использованную генерацию.

В UI указан Pro за 200 сом на 30 дней и ручной контакт через WhatsApp. Реальная ручная процедура выдачи доступа не описана кодом. Обещания активации в течение часа и приоритетной генерации не подтверждают соответствующих механизмов.

## Сценарии и приёмка

1. Пользователь создаёт проект, отвечает на интервью, получает blueprint. При повторном открытии план читается из базы. Другой пользователь не может прочитать или удалить его через приватный API.
2. Без AI-ключей поддерживаемые генераторы дают локальные результаты. Интерфейс не должен представлять этот режим как подтверждённый ответ внешнего AI.
3. При исчерпании лимита API возвращает код ошибки и UI объясняет причину. Ошибка генерации освобождает резервирование; успешный локальный fallback расходует его.
4. Пользователь редактирует 3D-деталь, отменяет и повторяет действие, экспортирует фактическую геометрию. Сохранение редактируемой сцены в серверную базу не входит в текущую основу.
5. Включённая проверка email закрывает приватные project/3D операции для неподтверждённого пользователя. Исключение: `/api/3d/providers` проверяет только наличие сессии и раскрывает лишь флаг конфигурации.
6. Reduced motion выключает декоративные эффекты. Возможность работать с геометрией остаётся доступной.

Эти критерии описывают ожидаемое поведение; перечень реально выполненных проверок хранится в [PROJECT_STATUS.md](docs/PROJECT_STATUS.md).

## Результат текущего этапа

Для 2D полного роста добавлен процесс «рисунок → настройка суставов → риг». Из JPEG/PNG/WebP создаётся встроенный WebP, доступна очистка белого фона; пользователь проверяет 19 точек. Результат содержит 14 костей, сетку с весами, клипы дыхания, приветствия и покачивания и сохраняется в JSON. Поза меняется перетаскиванием костей или числовыми полями, одна drag-операция отменяется одним шагом. Это skinning видимой иллюстрации; мимика и скрытые поверхности уровня Live2D остаются будущей работой. Контракт — [DESIGN_BACKEND.md](docs/DESIGN_BACKEND.md), интерфейс — [RIGGING_EDITOR.md](docs/RIGGING_EDITOR.md).

Реализованы `Rig2DDocument`, `Rig3DDocument`, `HouseDocument` версии 1; контракты ригов находятся в `src/shared/rigging`, контракт дома — в `src/shared/house`, хранение — в `src/backend/design`, приватные API вычисления/хранения и модель Prisma `DesignDocument`. 2D поддерживает FK, pivots, affine-матрицы, linear/step keyframes, loop и pose override; 3D — rigid FK с сохранением bind pose, repeat/mirror и локальных mesh; дом — прямоугольные комнаты, этажи, стены с открытыми проёмами и flat/gable roof. Сохранение использует ownership и optimistic revision: чужие документы дают 404, устаревшая запись — 409.

Вычисления локальные, без внешнего AI и расходования AI/3D-квот. Технические ограничения: 1 MiB на JSON-запрос, 100 документов на пользователя, общий лимит дизайн-API 60 запросов в минуту на пользователя в памяти одного экземпляра; limiter отключён в development. Новых тарифных обещаний нет. Ассеты 2D представлены HTTPS-ссылками либо встроенными PNG/WebP до 256 KiB. Клиент декодирует загруженные изображения; сервер проверяет MIME, сигнатуру и лимиты встроенных данных. Отдельного бинарного хранилища нет. Форматы — [DESIGN_BACKEND.md](docs/DESIGN_BACKEND.md).

Добавлена страница `/dashboard/rigging`: Canvas 2D, overlay костей в ConceptViewer, позирование, ключи, undo/redo, JSON и статический GLB. Design Engine переносит явные 2D/Live2D/VTuber-запросы в форму генерации рисунка. Старые 3D API отклоняют их до списания квот. Добавлен первый этап генерации рисунка: Cloudflare Workers AI + FLUX по умолчанию (JPEG с фоном), OpenAI Image API по явной настройке (WebP с запросом прозрачного фона). Для рисунка нужны серверные данные доступа; локальная сборка рига доступна после проверки суставов. Редакторы используют единые shared-evaluators; существующий GLB exporter не добавляет skinning. Новая таблица не применялась к рабочей базе. Статус проверок — [PROJECT_STATUS.md](docs/PROJECT_STATUS.md).

## Актуальный курс 2D Rigging Engine

[Полное ТЗ пользователя](docs/RIGGING_ENGINE_SPEC.md) задаёт собственный формат и ручной pipeline до AI-автоматизации. Текущий дополнительный этап: создание mesh выбранного слоя, независимые UV, изменение плотности, перемещение/добавление/удаление вершин с триангуляцией, undo/redo и переносимым JSON. Это не означает готовности параметрического лица, моргания, рта, физики, PSD и standalone runtime. Детали и ограничения — [RIGGING_EDITOR.md](docs/RIGGING_EDITOR.md).

## Соответствие 3D-запроса объекту

Класс размера в AI-генераторе задаёт только ориентир количества деталей. Он больше не навязывает архитектурные элементы категории landmark или автомобильное шасси всем vehicle-запросам. Название объекта, размеры и уточнения пользователя имеют приоритет над процедурным baseline; число деталей не требует добавления лишнего декора. Это исправление формируемого AI-запроса, не гарантия качества ответа внешней модели. Текущая геометрическая оценка связности не измеряет узнаваемость объекта.

## Редактор дома

Форма «Создать дом» отправляет описание в приватный `/api/house/generate`. AI сначала извлекает явно запрошенные помещения/размеры, затем предлагает порядок помещений и доли площади. Сервер делит прямоугольный контур по этим долям. Сервер вычисляет комнаты и проходы, проверяет покрытие, вход, связность комнат, перечень помещений и габариты. До одной повторной попытки плана при некорректном ответе; возврат суточной AI-квоты при ошибке. Результат устанавливается одной операцией с отменой, исходный документ сохраняется при отказе. Извлечение смысла остаётся AI-операцией и может ошибаться; проверка не подтверждает качество архитектуры или инженерную пригодность.

`/dashboard/house` открывается кнопкой «Редактор дома» в Design Engine. Это параметрический редактор с исходным планом 12×9 м, не автоматическое преобразование произвольной 3D-сцены или полное выполнение текстового задания. Комнаты и проёмы редактируются численно, план и 3D строятся из одного HouseDocument. Доступны разделение комнаты без проёмов, удаление комнаты вместе с её проёмами, до трёх этажей, цвет стен, крыша, просмотр выбранного этажа, undo/redo, локальный черновик, JSON import/export и статический GLB всего дома. Ошибочная правка не заменяет текущий документ.

Сохранение и открытие в аккаунте используют существующие приватные design-documents API и revision. В development `/playground/house` доступен без базы; production возвращает 404. Серверное сохранение в локальной среде не проверено из-за отсутствующей БД. Нет лестниц, мебели, инженерных расчётов, автоматического дизайна интерьера или генерации сложных mesh по тексту.

## Ручные деформеры 2D

Добавлены Warp и Rotation Deformer с иерархией, назначением группам mesh-слоёв, сдвигом, масштабом и поворотом. Warp имеет редактируемые управляющие точки; изменения сохраняются с ригом, работают с bone clips и общей историей. UV текстуры неизменны. Это следующий этап ручного pipeline; моргание, рот, физика и автоматическая подготовка слоёв ещё не реализованы. Контракт и ограничения — [DESIGN_BACKEND.md](docs/DESIGN_BACKEND.md).

## Параметры и ключевые формы деформеров 2D

Параметр задаёт диапазон, значение по умолчанию и ключевые формы одного Warp/Rotation Deformer. Между формами плавно интерполируются сдвиг, угол, масштаб и точки Warp. В редакторе доступны ползунок, создание/редактирование форм, ручные ключи параметра в клипе, linear/step, цикл воспроизведения и JSON import/export с историей. Независимые параметры сочетаются через вложенные деформеры. Это основа ручной анимации деформаций: прямые keyforms вершин/opacity, многомерное смешивание, готовая мимика и физика пока отсутствуют.

## Отрисовка сетки и названия анимаций

Текстурный mesh рисуется общими рёбрами через WebGL без отдельного Canvas clip каждого треугольника. При недоступном GPU/неподходящем внешнем изображении сохраняется Canvas-режим с предупреждением о возможных швах. Это исправляет отрисовку, а не качество весов, подготовку слоёв или мимику. Клип может иметь редактируемое название; внутренний ID сохраняется и не показывается вместо названия в кнопках.
