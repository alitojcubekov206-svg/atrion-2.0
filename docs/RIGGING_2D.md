# 2D-риггинг персонажей: целевая спецификация

Рабочий ручной редактор описан в [RIGGING_EDITOR.md](RIGGING_EDITOR.md), текущий контракт — [DESIGN_BACKEND.md](DESIGN_BACKEND.md). Главная уточнённая цель пользователя — [генерация персонажа и рига по тексту](CHARACTER_GENERATION.md) с качеством Live2D-образца. Эта цель ещё не реализована.

**Статус: FK, слои, ключи и ручной UI реализованы.** Ниже сохранены требования к дальнейшему развитию; конкретное текущее поведение определяется документами выше.

## Предложенный первый сценарий

Пользователь загружает отдельные прозрачные изображения частей персонажа, размещает слои, создаёт кости и pivots, связывает части со скелетом, задаёт ключевые кадры и воспроизводит клип. Первое предложение — жёсткая привязка части к одной кости и forward kinematics (FK). Не нужны вызовы AI для поворота сустава и проигрывания каждого кадра.

Единое изображение тоже можно показать как один слой, но оно не содержит скрытые части тела и суставы. Автоматическая сегментация цельного рисунка, дорисовка скрытых областей и деформация mesh не входят автоматически в этот сценарий. Их качество и инструменты определяются отдельно. Поддержка PSD, Spine, Live2D или иных редакторских форматов не заявляется без отдельного контракта и проверки.

## Документ и координаты

Предлагаемый `Rig2DDocument` хранит `schemaVersion`, `id`, название, размер холста, assets, layers, bones, attachments и animation clips. Эти имена пока не являются типами в `src/shared/types.ts`.

| Сущность | Необходимые данные | Инварианты |
| --- | --- | --- |
| Asset | ID, MIME, размер, стабильная ссылка либо файл пакета | Прозрачность сохраняется; blob URL не постоянное хранилище |
| Layer | ID, asset ID, порядок, visibility, transform | ID уникален; ссылка на asset существует |
| Bone | ID, parent ID, bind/local transform, длина | Без циклов, ненулевая длина, parent существует |
| Attachment | layer ID, bone ID, bind offset | Один выбранный тип привязки, смещение не меняется при вращении |
| Clip | ID, имя, duration, loop, tracks | Время ключей в пределах duration; target существует |
| Keyframe | Время, transform, interpolation | Числа конечны; ключи упорядочены; duplicate-time policy определена |

Предложение для 2D: пиксели, +x вправо, +y вверх в математической модели; экранные координаты с +y вниз преобразуются только на границе renderer/input. Углы в документе — радианы; UI может показывать градусы. Pivot и bind offset имеют явно обозначенное локальное пространство. Отрицательный scale как отражение требует отдельной проверки, нулевой scale не допускается. Несовместимую версию документа следует отвергать понятным сообщением либо явно мигрировать.

Мировой transform кости — произведение world transform родителя и local transform кости. Transform прикреплённого изображения — world transform кости и фиксированный attachment offset. Bind pose — исходное состояние; текущая поза и значения timeline не переписывают его. Перепривязка или смена parent должна явно выбирать: сохранить мировую позу либо перестроить локальный transform.

## Анимация и редактор

Предлагаемые панели: холст, дерево слоёв/костей, свойства выбранного объекта и timeline. Инструменты: выбор, перенос pivot/кости, создание дочерней кости, attach/detach, reset pose, постановка ключа, play/pause/scrub и undo/redo. Команда редактирования должна быть одним шагом истории после завершения drag.

В первой версии достаточно position/rotation/scale keyframes с явным linear или step режимом. Angle interpolation и петля должны иметь определённую семантику: движение через ±π по короткой дуге по умолчанию; полные обороты требуют unwrapped-углов. FPS задаёт частоту отображения/экспорта, но evaluator принимает время в секундах и не зависит от реальной частоты кадров.

Сериализованный JSON должен включать ссылки на ассеты либо экспортироваться с файлами ассетов; JSON без самих изображений не является автономным персонажем. Первый экспорт — документ/пакет для повторного открытия. GIF, видео, spritesheet и сторонние rig-форматы — отдельные решения, а не готовые exporters.

## Размещение и API: предложение

Чистые типы, FK и оценка clips — `src/shared/rigging/`; renderer, input, timeline — `src/frontend/rigging/`; страница — `/dashboard/rigging?mode=rig2d`. Backend использует тот же evaluator. Для JSON выделен дизайн-API с проверкой владельца и revision; API загрузки ассетов остаётся будущей задачей; не перегружать endpoints software-проектов.

Клиентский документ проходит полную структурную проверку до вычислений и сохранения: ссылки, циклы, лимиты количества, размеры, время, числа и MIME. Загружаемый SVG требует отдельной обработки активного содержимого; первоначальный PNG-вход может упростить эту границу. JSON-документ сохраняется через новый API; для загрузки бинарных ассетов object storage ещё не выбран.

## Приёмка будущего кода

1. Две кости длиной 100, child смещён на [100,0]. При повороте root на π/2 child endpoint [200,0] переходит в [0,200]; прикреплённая кисть сохраняет своё смещение.
2. Обнаруживаются цикл root→child→root, неизвестный parent/asset и NaN. Ошибка не повреждает открытый документ.
3. Reset pose восстанавливает bind pose; undo/redo возвращает геометрию и attachments без накопления ошибок.
4. Clip от 0 до π/2 за секунду в t=0.5 даёт π/4 независимо от FPS; play и scrub используют один evaluator.
5. Export→import восстанавливает дерево, слои, offsets, ассеты и ключи; пропущенный asset показан пользователю.
6. Preview доступен без AI-ключа. Неудачная загрузка/сохранение не теряет несохранённое редактирование.

Открытые решения: входные ассеты, минимальные форматы, допустимые размеры/количество слоёв, IK и mesh deformation, renderer и storage, экспорт анимации. Ручной слоевой workflow служит для исправлений. Пользователь выбрал генерацию по тексту, а не обязательную загрузку готовых слоёв.
