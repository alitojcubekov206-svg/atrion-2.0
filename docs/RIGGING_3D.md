# 3D-риггинг: целевая спецификация

Жёсткий 3D-риг и ручной интерфейс реализованы: [RIGGING_EDITOR.md](RIGGING_EDITOR.md). Чистый контракт в shared описан в [DESIGN_BACKEND.md](DESIGN_BACKEND.md).

**Статус: rigid-редактор реализован в рабочей ветке; skinning отсутствует.** Существующий `ThreeDConcept` описывает геометрические детали и может быть основой для первого рига. `parentId` у `ModelPart` сам по себе не реализует скелет. Незавершённые rig-файлы в другой локальной копии не входят в main и не переносились.

## Предложенная первая версия

Риг из жёстких деталей: пользователь добавляет кости, назначает parent и pivot, привязывает деталь к кости и меняет позу. Потомки движутся вместе с родителем. Это пригодно для примитивных персонажей и механических объектов; оно не деформирует общую поверхность по весам.

Отдельно решаются skinned mesh, weight painting, IK, retargeting, motion capture и импорт внешнего скелета. Нельзя назвать набор независимых поворотов деталей полноценной skeletal deformation. Первый этап может ограничиться FK и сохранением позы, а timeline добавляется после согласования общего clip-контракта с 2D.

## Контракт и вычисления: предложение

`Rig3DDocument` содержит schemaVersion, ссылку/вложенный geometry document, bones, bindings и pose; clips — если включены в выбранный объём. Bone: уникальный ID, parent ID, bind/local transform, pivot или head/tail в определённом пространстве. Binding: ID детали и bone ID плюс обратимый bind offset. При quaternion-представлении необходимо нормализовать и проверять rotation.

Математика 3D: +y вверх, +z спереди, правостороннее пространство; единицы сцены согласованы с `ThreeDConcept.units`. `ModelPart.size` остаётся полным bbox до вращения, `rotation` — XYZ в радианах. Изменение рига не должно менять значение `size` для представления угла. Преобразование новой quaternion-позы в существующий Euler-контракт проверяется отдельно.

Повторяющиеся и зеркальные примитивы представляют несколько instances. В первой версии либо связывается вся часть со всеми экземплярами, либо instances явно материализуются с новыми IDs. Этот выбор фиксируется в контракте; молчаливая привязка только одного экземпляра недопустима. `mesh.position` находится в локальном пространстве детали, трансформация не должна применяться дважды.

Данные bind pose и текущего pose разделены. Перемещение parent обновляет мировой transform потомков; прямое CAD-редактирование связанной детали должно явно обновлять offset или снимать binding. CSG, удаляющий связанные детали, требует удаления/переназначения ссылок с единым undo. Автоматическая привязка по названию/role может быть подсказкой, которую пользователь видит и исправляет.

## UI, экспорт и хранение

Реализована отдельная страница `/dashboard/rigging?mode=rig3d` с тем же `ConceptViewer`. Design Engine передаёт модель через sessionStorage; кнопки находятся в боковой панели. Нужны дерево костей, просмотр pivots, выбор bindings, свойства сустава и reset pose. Взрывной вид и декоративная сборка не должны смешиваться с исходными rig transforms.

Версионированный JSON сохраняет риг, геометрию и pose. Существующие GLB/STL/OBJ/PLY/USDZ exporters экспортируют геометрию; код skeleton/skin export в них не внедрён. Запечённая поза в GLB — статическая модель. Экспорт анимационных костей/skin требует отдельного изменения и проверки импорта в целевом редакторе.

Чистый FK и проверки — shared; редактирование и overlay — frontend. Backend нужен для постоянного хранения и проверки документов, не для каждого движения. Для этого добавлены `DesignDocument` и приватный дизайн-API.

## Приёмка будущего кода

1. Поворот parent переносит child и связанную деталь; локальное смещение сохраняется.
2. Bind pose после reset совпадает с исходным, включая вложенные transforms, repeats/mirrors и mesh.
3. Циклы, отсутствующие part IDs и нечисловые/quaternion transforms отклоняются без повреждения сцены.
4. Undo/redo атомарно возвращает кость, binding и геометрию после reparent/CSG/delete.
5. JSON round trip возвращает дерево и pose. Статический экспорт совпадает с видимой позой и подписан как статический.
6. Если выбран skinned export, внешний импорт действительно содержит bones, weights и animation, а не только узлы сцены.

Первый риг — rigid. Открытые решения: деформируемые поверхности, произвольные импортированные модели, область timeline, формат экспорта и хранение. Основной фокус проекта остаётся 2D-риггингом.
